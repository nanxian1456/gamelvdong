# 提交规范

本规范用于保持项目的 Git 历史清晰、可回溯。每次提交只解决一个明确问题，并保证提交后的代码可以运行和测试。

## 提交前检查

提交前从项目根目录运行完整测试：

```powershell
node --test
```

同时确认：

- `git status` 中只包含本次改动需要的文件。
- `CHANGELOG.md` 已增加本次提交的修改人、北京时间、修改内容和涉及范围。
- 没有提交 `.env`、令牌、密码、私钥或其他敏感信息。
- 没有提交 `node_modules/`、`coverage/`、日志及编辑器临时文件。
- 新增或修改的命令、路径和链接能够实际使用。

## 提交信息格式

提交信息使用以下格式：

```text
<类型>(可选范围): <简短说明>
```

类型使用小写英文，说明使用简洁的中文或英文祈使句，不加句号。例如：

```text
feat(rhythm): 增加长按音符判定
fix(storage): 修复旧版存档迁移
docs: 补充本地运行说明
```

常用类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增用户可见功能。 |
| `fix` | 修复缺陷。 |
| `refactor` | 调整代码结构且不改变外部行为。 |
| `test` | 新增或修改测试。 |
| `docs` | 只修改文档。 |
| `style` | 不影响逻辑的格式调整。 |
| `perf` | 性能改进。 |
| `chore` | 仓库配置、工具或其他维护工作。 |

如果改动不兼容旧行为，在类型或范围后添加 `!`，并在正文中说明迁移方式：

```text
feat(storage)!: 更新赛季存档结构
```

## 提交粒度

- 一个提交只包含一个可独立说明的改动。
- 功能代码、对应测试和必要文档应放在同一提交中。
- 不要把无关格式化、重命名或临时调试代码混入功能提交。
- 提交前使用 `git diff --staged` 检查最终内容。
- 已推送的共享提交不要随意改写历史；需要修正时优先追加新提交。

## 分支命名

直接维护 `main` 时，提交前必须确保测试通过。需要独立开发时，从最新 `main` 创建短期分支：

```text
feat/<简短主题>
fix/<简短主题>
docs/<简短主题>
refactor/<简短主题>
```

例如：`feat/new-song`、`fix/pause-timing`。分支合并后及时删除远程和本地短期分支。

## 修改日志

每次提交都必须同步更新根目录的 [`CHANGELOG.md`](../CHANGELOG.md)，包括文档、测试、重构和内部维护改动。修改日志面向不熟悉 Git 命令的读者，Git 历史仍是完整差异的最终依据。

提交前按照下面的格式，在“已提交记录”表格顶部增加一行：

```markdown
| 时间（北京时间） | 修改人 | 类型 | 修改内容 | 涉及范围 |
| --- | --- | --- | --- | --- |
| 2026-10-10 01:00 | nanxian1456 | 文档 | 说明本次完成的具体结果。<br>同一提交的第二项结果。 | `CHANGELOG.md`、`docs/提交规范.md` |
```

- 时间统一使用北京时间（UTC+8），精确到分钟。
- 修改人使用 GitHub 用户名；无法确认时使用 `git config user.name` 显示的名称。
- “修改内容”说明实际结果，不写“优化了一些内容”等无法核对的描述。
- 同一条记录包含多项修改时，在单元格内使用 `<br>` 换行，不要拆成多个提交人或时间相同的表格行。
- “涉及范围”可以列出主要文件、目录或模块，不需要罗列每一个文件。
- 提交前把本次内容从“未发布”移入对应日期；已推送记录发现遗漏时，使用新的提交补充，不改写共享历史。
